# 发布流程的设计思想

这份文档写的是**为什么这么做**，不是怎么敲命令。换到别的机器、别的工作区时，
照着这些约定重写一份脚本就行，不必套用现有的 `build.ps1`。

## 一、产物怎么命名

    <名字>-v<版本>-<平台>-<架构>[.exe]

- 名字：客户端 `EndfieldMonitor`，采集端 `enf-collector`，增强版 `enf-collector-plus`
- 平台：只有 `win` 与 `linux` 两种写法
- 架构：只有 `x64` 与 `arm64` 两种写法

**为什么**：早先客户端写 `win-x64`、采集端写 `windows-amd64`，同一个东西两种叫法，
下载页上看着乱。统一之后，任何一段脚本都能靠文件名推出手上的东西是给谁的。

产物名里的版本**带 v**（`-v0.6.0-win-x64`），程序内部嵌的版本**不带 v**（`0.6.0`）。
比较版本时统一按不带 v 的算。

## 二、编哪些东西

三个平台 × 三类产物：

| 类别 | 每平台几个 |
| --- | --- |
| 客户端 | 1 |
| 采集端（普通） | 1 |
| 采集端（增强版） | 1 |
| 套件包（zip） | 1 |
| 合计 | 4，三层平台共 12 个 |

**套件包**是「客户端 + 该平台的增强版采集端 + 一份怎么用」打成的 zip。
它的意义是让同机自看变成一步：客户端启动时先探本机端口，没人监听就把同目录里的
采集端拉起来并连上，用户不用开第二个窗口。

## 三、版本号怎么进去

- 采集端：`go build -ldflags "-s -w -X main.version=0.6.0"`，代码里 `var version = "dev"`
- 客户端：`dotnet publish -p:Version=0.6.0 -p:InformationalVersion=0.6.0`，
  运行时从 `AssemblyInformationalVersion` 读

**为什么**：两端都要能自己报出版本，更新检查才有依据。源码里直接跑时是 `dev` / `0.0.0`，
一眼能看出不是发行版。

## 四、往哪儿发

两个平台分工不同，别搞成对称的：

| | Gitee（主仓库） | GitHub（代码镜像） |
| --- | --- | --- |
| 代码与标签 | 推 | 推 |
| 发行版产物 | 发，**只留最近两版** | 不发 |
| 原因 | 附件配额只有 1 GB，全量发几版就撞墙 | 本地网络到 GitHub 太慢（实测单次 API 约 3 秒），大文件传不上去 |

历史版本不归档，需要旧版的让使用者在 issue 里提。**这是刻意的选择**：项目还在快速
变动，先不做版本发布管理。

### 配额这件事

Gitee 的**仓库空间**（5 GB）与**发行版附件配额**（1 GB）是两笔独立的账。
代码几乎不占空间，撞墙的永远是附件。而且 Gitee 的 API **没有删附件的接口**，
想腾空间只能把整个发行版删掉（tag 会留着，代码不受影响）。

## 五、发布脚本必须守住的事

这几条都是踩过坑换来的：

1. **构建前先停掉自己在跑的产物**。Windows 上覆盖运行中的 exe 会静默失败，
   表现为"构建好像成功但东西没变"。
2. **重跑要幂等**。发行版已存在就取回来复用，附件已存在就跳过。
   取发行版用**按 tag 直查**的接口，不要"列出全部再筛"——后者在脚本里行为不确定。
3. **上传失败要重试**，并且**把服务端返回的错误正文打出来**。
   只报状态码的话，「400」会让人往文件本身猜，而真正的原因（配额、权限、限流）就在正文里。
4. **拿不到确定的发行版 id 就停下**，不要带着空 id 继续跑——那样会失败一长串，
   看起来像是文件的问题。
5. **逐个显式推标签**，不要批量推。
6. **令牌只从环境变量或家目录下的文件读**，绝不写进仓库；输出里也要把它遮掉。
7. **生成校验和**（`SHA256SUMS.txt`）并跟产物一起发。
8. **用 PowerShell 重写时，当心 `Invoke-RestMethod` 返回 JSON 数组的方式**：
   它把顶层数组当成“一个对象”返回，外面再套一层 `@()` 就成了“只含这一个数组的数组”。
   后果很隐蔽：`foreach` 只走一圈、`$_.tag_name` 是全部 tag 拼起来的字符串，于是
   **排序静默失效**（“前两个”取到的其实是最老的两个，把真正该留的删了），
   **筛选条件恒为真**（数组与字符串用 `-eq` 比较会返回匹配元素，非空即真，
   曾因此筛出四个 id 拼出一条废 URL，让十三个文件全部上传失败）。
   应对：拿到返回值直接遍历，不套 `@()`；需要数量时显式数元素。
   （这一条只在用 PowerShell 重写时适用；用 bash 或 Python 不会碰到。）

## 六、发布说明

优先用 `publish/RELEASE-<版本>.md`；没有就自动生成一份附件清单。
说明要写清：这一版做了什么、**哪些没验证过**、已知问题。没验证的部分别含糊过去。

同时维护一份 `CHANGELOG.md`：每次发布往 `<!-- 新的在上面 -->` 那行下面插一条
「版本号 + 一句话说明」，说明取自发行说明的第一个小标题；那个标题太通用
（比如「本版做了什么」）就往下取一层，标题本身太通用时就把二级标题用上。
已经记过的版本要跳过，重跑发布不能重复加。

顺序上，这一步要在推送代码**之前**做完，好让这条记录跟同一轮推送一起上去。

## 七、这套东西不适用的地方

- **GitHub 当产物仓库**：配额其实很宽松（单个 release 最多 1000 个附件、单文件 < 2 GiB、
  总量与带宽都不限），问题纯粹是本地网络到它太慢。网络条件变了这条结论就该重估。
- **Gitee 的 1 GB 附件配额**：只对免费账号成立。
- **Linux 侧的一切**：图标采集、启停、更新替换脚本，都还没在真机跑过。
